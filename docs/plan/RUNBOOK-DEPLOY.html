Deploying WattUp

Two Next.js applications, one Postgres database, and one setting that stops everything if it is wrong.

Written 3 Sep 2026 Against commit ccb488c Canonical copy docs/plan/RUNBOOK-DEPLOY.md
Read this before opening Vercel

This repository is not a pnpm workspace, and must not become one. Each app has its own lockfile and installs independently. That means two Vercel projects, each with its Root Directory set to the app folder.

A project built from the repository root will not find an application. This is the step everything else waits on.

02

The database

Already provisioned on Neon. Both apps point at the same one. Nothing to create.

There are twelve migrations. The most recent, 20260903100000_rbac_permissions, creates the proforma_member view that the pro-forma gate reads. Until it is applied, the pro-forma app can admit nobody.

# wattup-frontend is the only app that may do this
cd wattup-frontend
pnpm install
DATABASE_URL='<production url>' pnpm migrate:deploy

migrate:deploy applies what is pending and never resets. Use it — not migrate:dev, and never db push.

After the first deploy, this runs itself

The frontend's build runs scripts/migrate-on-deploy.mjs before next build, so a production deploy applies pending migrations on its own. You run the command above only for the first deploy, or to migrate without shipping code.

Why it is guarded to production only

There is one database, shared by both apps, with no preview or branch database configured. Without the guard, every Preview deployment would migrate production — so a pull request carrying a bad migration would alter live data before anyone reviewed it.

VERCEL_ENV must be exactly production; anything else, a local pnpm build included, skips and says so in the log. A missing DATABASE_URL on a production build is refused, and a failed migration fails the build rather than shipping code whose schema change did not land.

Migrations must be additive

Vercel runs the build before it promotes the deployment, so a migration takes effect while the previous version is still serving traffic. Adding a column or a table is invisible to that older code; dropping or renaming one breaks the running site for the length of the build.

Split a destructive change across two releases: add the new shape and write to it, ship, then remove the old shape once nothing reads it. If you later want migrations on Preview too, the clean answer is a Neon branch database per preview — not a looser guard.

Never put this in a build command

pnpm db:seed writes to whatever DATABASE_URL points at. It force-promotes ADMIN_EMAIL to SUPER_ADMIN and recreates that account from ADMIN_PASSWORD. It ran on every production build until finding F13 removed it.

To create the first administrator, use pnpm seed:admins instead — it touches user and account only, and adds nobody who is not in ADMIN_EMAILS.

This one stays manual deliberately, unlike migrations: automating it would put ADMIN_PASSWORD permanently in Vercel, and an admin you deleted would come back on the next deploy.

Verify

psql "$DATABASE_URL" -c "select count(*) from _prisma_migrations where finished_at is not null;"
psql "$DATABASE_URL" -c "select count(*) from proforma_member;"

# The view must exist. Zero rows is fine here; a missing relation is not.
03

Generate the secrets

Three values, and two of them must not match.

openssl rand -base64 32   # -> wattup-frontend  BETTER_AUTH_SECRET
openssl rand -base64 32   # -> wattup-proforma  BETTER_AUTH_SECRET
openssl rand -base64 32   # -> wattup-frontend  CRON_SECRET
The two auth secrets must differ

They are what keep the two apps' sessions separate on a shared parent domain, so rotating one does not sign out the other's users. The cookie prefix (wup for the pro-forma) separates the cookie names; the secret separates the trust.

Rotating a BETTER_AUTH_SECRET invalidates every existing session for that app.

The scheduled job

vercel.json already declares it, so there is nothing to click:

{ "crons": [{ "path": "/api/cron/purge-activity-log", "schedule": "17 3 * * *" }] }

Vercel registers it on every deploy and sends Authorization: Bearer <CRON_SECRET>; the route compares hashes and answers 401 to anything else. There is no manual step here — setting CRON_SECRET once is the whole job.

07

Create the first administrator

Public registration is closed twice over, so this is the only way in.

cd wattup-frontend
DATABASE_URL='<production url>' \
ADMIN_EMAILS='someone@wattupusa.com' \
ADMIN_PASSWORD='<a strong password, used once>' \
pnpm seed:admins

Then sign in at /admin and change that password immediately.

Grant ACCESS_PROFORMA from the dashboard to whoever needs the builder. Until someone has it, proforma_member is empty and the gate admits nobody — which is correct, not a fault.

09

Rollback

Promoting a previous deployment is instant. Two things it will not undo.

Vercel keeps every build — promote the previous deployment from the Deployments tab; no rebuild needed.

  • Migrations are forward-only here. A schema change that breaks the previous build cannot be undone by promoting it. Read a migration before applying it to production.
  • Seed effects persist. A promoted user stays promoted.

To close the gate immediately without a deploy: remove ACCESS_PROFORMA from every role and user in the dashboard. proforma_member empties and the gate admits nobody on the very next request, because the session is read from the database and not a cookie cache.

10

Known issues to weigh first

None of these block a deploy. All of them are better known than discovered.

  1. Cache-Control: no-store is applied to every path in the pro-forma, including /_next/static/*. Those files are content-hashed build artefacts, identical for every visitor, carrying no user data. The header forces a full re-download of the app shell on every load and is the single largest repeat-load cost in that app. Narrowing it is a deliberate security decision that has not been made.
  2. pnpm lint fails in wattup-frontend — 17 errors across fourteen files, pre-existing and unrelated to recent work, though that app's own CLAUDE.md says lint must pass. It does not block a build.
  3. F17, Cloudinary separation, is still open.
  4. The break-glass admin account is still an open client question: whether it should exist at all.
  5. Sessions have been observed disappearing from the session table unexplained during development. If users report spurious sign-outs after launch, start there.

  1. Apply migrations pnpm migrate:deploy — first deploy only; production builds migrate themselves after that
  2. Generate 3 secrets openssl rand -base64 32 ×3 — two must differ
  3. Vercel project A Root Directory = wattup-frontend
  4. …its env 13 required, plus CRON_SECRET
  5. Vercel project B Root Directory = wattup-proforma
  6. …its env exactly 6; it 503s and names any missing
  7. Domains wattupusa.com and proforma.wattupusa.com
  8. Resend verify the domain, add DKIM + SPF
  9. First admin pnpm seed:admins, then change the password
