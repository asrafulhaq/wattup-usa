The brief, as given
Client request · 1 September 2026

“Wattup has already signed up the following locations and is currently setting up their machines. They need a similar map and location-finder functionality to the Ionna example, but better — more functional, faster, and aesthetically polished.

Need the initial version done by this Friday. The same map/system will also be reused for Wattup’s expansion across Asia, from Singapore to Thailand and other markets later this year, so make sure the setup is scalable and easy to expand.

Plan this out and report back on how you’re going to approach it, including which map library/platform and frameworks you would use, the overall architecture and data structure, how search and location functionality will work, the performance and optimisation approach and how we should structure it for future expansion.

The Ionna map is just a reference — aim for a better, faster, more modern, and visually polished experience. No matter if we need Three.js or React Fiber, GSAP or anything — just tell me exactly which map library we need. If it is paid that is also fine, but I need exactly this look. The map and UI in the reference is in black mode, but we will do light mode. We will also manage this from the dashboard, and put it all in the seed file so we can seed on first run and manage everything from the dashboard afterwards.”

Five things in that brief each changed a decision in this plan, so they are worth pulling out:

  • “Exactly this look, paid is fine” — this is what settles the platform question. The reference frame is defined by everything that has been stripped out of the basemap, and per-layer control over that is precisely what you pay Mapbox for.
  • “Light mode, not black” — the style gets rebuilt on a near-white ground with WattUp blue as the single accent. This is not an inversion: on a light ground the markers need more weight and less glow than the reference, or they disappear.
  • “Three.js, React Fiber, GSAP — whatever it takes” — the honest answer is that a second WebGL layer would cost frames and add nothing, because the map is already WebGL. GSAP does the parts that genuinely need it. Detail in the alternatives section.
  • “Reused for Asia later this year” — the reason market, country and distance units are in the schema on day one rather than added in December.
  • “Seed first, then manage from the dashboard” — the data workflow, described in the next section.
The decision you need to make
Build it on Mapbox GL JS, behind the react-map-gl wrapper.

Mapbox is the only mainstream platform where the reference look is a design task rather than a fight. Mapbox Studio is a visual editor for the basemap itself: turn off every road, POI and label, recolour land and water to flat greys, and you have the reference frame exactly, in light mode, in an afternoon. Because we sit behind react-map-gl, the same component code runs on MapLibre if you ever want off the invoice.

Cost at our size
50,000 map loads/month free, then $5 per 1,000. A marketing page at this traffic is almost certainly $0.
Asia
Full Singapore and Thailand coverage day one, with local-script labels available from the same style.
Escape hatch
MapLibre + self-hosted Protomaps tiles is a drop-in swap, roughly one day, if cost or vendor lock ever bites.

What the references actually specify

I pulled the 239 frames out of the interaction GIF to see what moves. Three things define that design, and only one of them is the map:

  • A tab strip across the top — six locations, each with a name, a region line and two data lines, with a thin accent bar that slides between them. The map re-centres as the bar moves. This is a component we write, not a map feature.
  • A deliberately empty basemap — flat grey landmasses, no roads, no POI labels, a dashed connector line and small dot markers. The polish comes from what has been removed. That is a Mapbox Studio style, plus one custom GeoJSON layer for the region shapes.
  • One accent colour, used sparingly — the selected marker glows, its card is solid fill, everything else is grey. In light mode this becomes WattUp blue #197dff, already the primary token in globals.css. I would keep amber strictly for "coming soon" status, so the accent never competes with a state.

The second reference — the address/zip bar with a distance selector, a filter tray and Use My Location — is the functional half. It sits above the map on desktop and collapses into a sticky pill on mobile. That layout is settled; the detail is in the search section below.

On the tooling question you raised: we do not need Three.js or React Three Fiber. Mapbox GL is already a WebGL renderer, and putting a second WebGL context on the page costs frames and battery for no visual gain. GSAP is already installed and is the right tool for the sliding indicator and card transitions; framer-motion and vaul — also already installed — cover the list and the mobile sheet.

Architecture

Locations become a first-class record in the database you already have, managed from the dashboard you already have. Nobody should need a deploy to add a site or flip one live.

Neon Postgres ── Prisma Location model
      │            managed in the existing /dashboard, RBAC already in place
      ▼
server component  'use cache' + cacheTag('locations')
      │            same pattern as siteSettings today; edits revalidate the tag
      ▼
/locations       server-rendered shell: SEO copy, JSON-LD, full list in HTML
      │            crawlable and useful with JavaScript switched off
      ▼
<LocationFinder>  client island, state lives in the URL
      ├── <MapCanvas>    dynamic import, mounts on viewport intersection
      ├── <SearchBar>    address/zip · distance · filters · use my location
      ├── <ResultsList>  desktop panel  /  vaul bottom sheet on mobile
      └── <MarketTabs>   the sliding-indicator strip from the reference

/locations/[slug] one static page per site
                   "EV charging on W Colton Ave, Redlands" — the SEO surface

Why the database, not a JSON file data

A file means a developer and a deploy for every status change. There are 27 sites today and 16 of them flip status during 2027 — that is a year of small deploys avoided.

Why a page per station seo

"EV charging near Redlands" is a query someone types. A map alone is invisible to that; 27 indexed pages with LocalBusiness schema are not.

Why URL state ux

Filters and selection in the query string means back works, links are shareable, and support can send a customer straight to a station.

Why geocode once perf

Addresses become coordinates at import time and are stored. Nothing geocodes at page load, so the map has nothing to wait for.

Seed first, dashboard after

The 27 sites go into prisma/seed.ts, which this repo already runs — db:seed is wired in package.json and build calls it. One command populates a fresh database; from that moment on, every change happens in the dashboard and nobody touches the seed again.

// prisma/seed-data/locations.ts — generated once from the CSV, then committed
export const locationSeed = [
  {
    slug: 'redlands-w-colton-ave',
    name: 'WattUp Redlands',
    status: 'PLANNED',
    goLiveQuarter: 'Q3 2026',
    street: '1405 W. Colton Ave', city: 'Redlands',
    region: 'CA', postalCode: '92374', country: 'US',
    latitude: 34.0639, longitude: -117.2231,   // geocoded at import, baked in
    market: 'us-ca', timezone: 'America/Los_Angeles',
    chargerCount: 2,
  },
  // … 26 more
]

Coordinates are baked in, not fetched offline

Geocoding runs once in a separate import script and the results are written into the seed file. Seeding therefore needs no Mapbox key, no network, and gives the same answer every time — on your machine, in CI, and on a new laptop.

Re-running the seed is safe idempotent

Every row is an upsert keyed on slug, so running it twice creates nothing twice. It also means build can keep calling it, as it does today, without surprises.

The seed never overwrites dashboard edits important

This is the part that usually goes wrong. Once a row has been touched in the dashboard it carries managedInDashboard: true, and the seed skips those rows on update. Otherwise the next deploy would quietly revert a status someone changed that morning.

After seeding, the dashboard owns everything workflow

Add a site, edit an address, flip PLANNED to LIVE, publish or unpublish — all in /dashboard/locations, reusing the RBAC and the Cloudinary upload flow already in the project. Saving revalidates the locations cache tag, so the public map updates without a deploy.

One extra piece worth building on Wednesday while the import script is open: geocoding on save in the dashboard. When someone types a new address, the form resolves it to coordinates and shows a small map preview for confirmation. Without it, the first location added after launch has no coordinates and silently never appears on the map — which is exactly the sort of bug that surfaces three weeks later.

Data model

Written for the second market, not the first. market, country, timezone and distanceUnit exist from day one so that Singapore is rows in a table rather than a refactor.

// Prisma schema
model Location {
  id            String   @id @default(cuid())
  slug          String   @unique     // redlands-w-colton-ave
  name          String               // public site name, not the owner LLC
  status        SiteStatus           // LIVE | UNDER_CONSTRUCTION | PLANNED
  goLiveQuarter String?              // "Q3 2026" — drives the "coming" chip

  // address, split so it can be formatted per market
  street        String
  city          String
  region        String               // CA · Central Region · Bangkok
  postalCode    String
  country       String               // ISO-3166: US, SG, TH
  latitude      Float
  longitude     Float

  // market registry key — one row per market in config, not code
  market        String               // "us-ca" | "sg" | "th"
  timezone      String               // America/Los_Angeles

  // what a driver actually wants to know
  chargerCount  Int
  connectors    Connector[]          // CCS1 / NACS / CCS2 / CHAdeMO
  maxPowerKw    Int?
  amenities     Amenity[]            // restroom, food, retail, lighting, canopy
  access        AccessType           // PUBLIC_24_7 | HOST_HOURS
  hours         Json?

  // internal — never serialised to the browser
  ownerEntity   String?
  apn           String?
  salesRep      String?
  siteScore     Float?
  internalNotes String?

  publishedAt   DateTime?
  @@index([market, status])
  @@index([latitude, longitude])
}

The public endpoint selects an explicit field list, never the whole row, so an internal column cannot leak by being added later. It ships as GeoJSON because that is what the map consumes natively — one shape, no transform on the client.

Before we publish anything — three flags on the spreadsheet

The sheet carries private data that must not reach the website

It holds the property owner's legal entity, their notice address, the parcel number and the sales rep for every site. Several notice addresses are plainly residential — one is a home in Beverly Hills. Publishing those would expose your landlords' home addresses and hand your pipeline to competitors. The public record is: site address, city, state, postcode, charger count, status. Everything else stays behind the dashboard login.

"Rating out of 5" is an internal site score, not a customer review

Shown next to a station on a public map, a 3.7 reads as "other drivers rated this poorly", which is both wrong and unhelpful. My assumption is that it stays internal. If you want stars later, they should come from real driver feedback.

No site is live yet, and the map must say so

All 27 are signed and in build — 11 with switchgear ordered for 2026, 16 for 2027. A driver who taps a pin and drives there will find nothing. Every marker carries a status chip, "coming soon" sites use a hollow marker against solid for live, and the default filter can be set either way. This also turns the map into a leasing asset: it shows momentum rather than pretending to be a network.

Search and location behaviour

Address or postcode geocode

Mapbox Search Box with autocomplete, debounced at 250 ms and biased to the active market. Session tokens keep the billing on one search, not one keystroke.

Use my location browser

The browser Geolocation API: one tap, permission asked at the moment of intent rather than on load. A clean fallback message when it is refused, because a fair number of people do refuse.

Distance client

5 / 10 / 25 / 50 / 100 with the unit taken from the market — miles in California, kilometres in Singapore. Filtering is a haversine pass over data already in memory, so it is instant.

Filters client

Status, connector type, minimum chargers, amenities. Every filter shows its result count and nothing ever returns a blank screen with no explanation.

Free text client

Fuzzy match on city and site name across the whole set, resolved locally in well under a frame. Even 500 sites is a payload smaller than one hero image.

List and map are one thing ux

Hovering a card lifts its marker, selecting flies the map and opens the card, and the list is always sorted by distance from the current search point.

// every piece of state is in the URL — shareable, back-button-safe, SSR-able
/locations?market=us-ca&near=34.056,-117.195&label=Redlands%20CA
          &radius=25&status=live,soon&connector=nacs&sel=redlands-w-colton-ave

Empty states do real work: "No stations within 25 miles. The nearest is Loma Linda, 38 miles away" with a button that widens the radius — rather than an empty list, which is where most finders lose the visitor.

Performance

A map library is heavy — roughly 200 KB gzipped before a single tile. The plan is that it never sits in front of the first paint.

  • The map is not in the initial bundle. It is dynamically imported when its container approaches the viewport. Until then the slot holds a styled placeholder rendered on the server, so the largest paint never waits on WebGL.
  • Markers are WebGL layers, not DOM nodes. One GeoJSON source with clustering, drawn as symbol layers. DOM markers are fine at 27 and fall apart at 500; doing it right now means the Asia rollout changes nothing.
  • Data is cached, not fetched per visit. use cache with a locations tag, revalidated when the dashboard saves — the pattern already running for site settings.
  • Station pages prefetch on hover, so opening one from the list is instant.
  • Motion respects the system reduced-motion setting. With reduced motion on, the map jumps rather than flies and the marker pulse is dropped.

Budgets I will hold the build to: LCP under 2.0 s on a mid-range phone over 4G; map interactive within 1.5 s of entering the viewport; 60 fps while panning; and the /locations document itself under 40 KB gzipped before the map loads.

Adding Singapore, Thailand, and whatever follows

The test of this build is not California. It is whether the second market costs a week or a day. Each market is one config file plus rows in the table:

markets/sg.ts
  center: [103.8198, 1.3521]   defaultZoom: 11   bounds: [...]
  distanceUnit: 'km'           currency: 'SGD'   locale: 'en-SG'
  addressFormat: 'sg'          geocodeBias: 'SG'
  labelLanguage: 'en'          // 'th' for Thailand, Thai script from the same style
  • Routes: /locations stays the US surface; new markets get /sg/locations and /th/locations. Path segments rather than a query parameter, because each market needs to rank on its own in local search.
  • Units and formats are never hardcoded. Distance, address order and phone format all read from the market config. Writing "mi" into a component today is what makes the Singapore launch expensive.
  • Copy is externalised from the start so Thai translation is a file, not a hunt through JSX. Thai also needs a font with proper script coverage — worth settling before we have a page full of it.
  • The map style is shared. One Studio style, all markets; only the camera and the label language change.
  • The market strip — the sliding-indicator component from the reference — becomes the market switcher once there is more than one. It is built for that on Friday even though it will show one entry.
